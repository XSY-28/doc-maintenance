# 文档职责、增长和历史

## 每项事实有主要归属

先查看已有文件能否承担责任，再考虑增加文件。可按以下职责判断，不强制项目采用相同目录或文件名：

| 文档 | 读者应得到什么 |
|---|---|
| 入口 README | 用途、适用范围、当前能力、最短可用路径及下一步 |
| 架构总览 | 系统组成、关系和重要约束；链接到下层具体行为 |
| 模块参考 | 配置、接口、行为、失败、限制和扩展方式 |
| 教程/操作指南 | 前置条件、顺序步骤、可观察的成功结果、常见失败的恢复 |
| 决策说明 | 为什么采用方案、放弃了什么、适用前提和验证缺口 |
| AGENTS.md | 在该范围持续适用的短规则和细节链接 |

同一事实的长篇解释只维护一个主要位置。其他位置保留必要摘要并使用可检查的相对链接。调用者必须知道的条件、异常或完成时机可以就地简述：链接不能让当前入口失去可用性。先读更深层的拥有者再调整上层概述，不先把放错位置的内容润色得更长。

## 教程和参考采用不同结构

教程按读者的已有知识安排前置概念和步骤。先完成一个真实任务，再引入更深的可选内容。参考文档按查询对象组织，内容可以详尽。短文用清晰小节区分两种用途，避免为分类而拆出许多新文件。

入口说明面向用户能做什么、看到什么；内部实现细节放到相应深度。入口摘要应写读者能获得的能力、适用时机与主要代价，不写内部注册、私有组件或实现身份流水账。目录和摘要在长文中帮助定位，短说明不必套全套栏目。

长篇参考（尤其自动生成的配置、工具或接口目录）不靠统一全文上限裁剪事实，而应在详尽条目之前提供紧凑入口层：适用范围、分组索引、稳定锚点与概念说明链接。判断长文档是否该拆分时，优先看单次查询需要扫过多少无关内容，按已有稳定领域拆分，不按字数机械切块。

仓库级规则与契约留在项目文档（如 `AGENTS.md` 或 `docs/`），Skill 只承载薄工作流；避免把长期约束藏在 Skill 里，导致未调用该 Skill 的 agent 漏掉规则。

## 篇幅预算

只约束实际容易膨胀的常驻文件。`.doc-maintenance.json` 的 `budgets` 记录具体路径、计量单位和上限。超过上限时：

1. 将不属于该层级的细节移到其主要归属，修复入链。
2. 删除重复和无关叙述，保护所有必要事实。
3. 内容确有必要且无法合理迁移时，说明理由并调整预算。

上限是防膨胀的护栏，采用“棘轮”思路更有效：篇幅已在目标线内时，随内容回落同步收紧上限并保留约 5% 工作余量；高于目标线时先冻结上限（新增内容必须通过迁移或精简腾出空间），回落到目标线后再恢复余量。预算与余量按项目决定，工具不自动收紧或扩大。英文 `words` 按空白分词；`characters` 数非空白 Unicode 码点，适合明确约束中文/混合文本。两者都计入代码与表格，不是阅读难度评分，也不是模型 token 预算。不要用同一数字直接比较两种单位。

## 当前状态和历史

现行说明写现在的行为，决策说明保存理由与取舍，历史档案保留当时证据。使用项目既有提案、ADR 或设计记录体系即可。正文和图表中不要散落“已实现 / future”这类会过期的状态标注；尚未定案的假设、草稿或临时记录放进明确标明非权威的草稿区或 issue。

- **写新清旧**：新增决策记录时，顺手核查同一主题的已有记录，在同一次改动中归档、关联或删除被替代的旧记录，不把清理攒到以后。
- **按未来决策价值分类**：
  - 小范围 UI 调整或纯机械变动形成的已实现记录：直接删除并修复或清理入链。
  - 仍约束后续边界、契约、安全规则或重启条件的记录：保持活跃，并同步事实位置和名称。
  - 已完成且不再指导日常修改、但有历史背景价值的记录：转入只读归档；归档后不再为统一文风改写正文，也不校验其出链，只更新活跃文档指向它的入链。
  - 被否决的提案：只有当该想法仍具诱惑力、保留理由能防止重犯时才保留；前提已过时的直接删除。
- 机械小改动优先更新已有说明；需要长期保留、且源码和测试无法表达的理由才值得新增决策记录。

篇幅治理不等于按年龄或配额删除历史。移动、删除或合并说明前先查看入链；保留独特理由及已知验证缺口。
