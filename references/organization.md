# 文档职责、增长和历史

## 每项事实有主要归属

先查看已有文件能否承担责任，再考虑增加文件。可按以下职责判断，不强制项目采用相同目录或文件名：

| 文档 | 读者应得到什么 |
|---|---|
| 入口 README | 用途、适用范围、当前能力、最短可用路径及下一步 |
| 架构总览 | 系统组成、关系和重要约束；链接到下层具体行为 |
| 模块参考 | 配置、接口、行为、失败、限制和扩展方式 |
| 教程/操作指南 | 前置条件、顺序步骤、可观察的成功结果、常见失败的恢复 |
| 决策说明 | 为什么采用方案、放弃了什么、适用前提和验证缺口 |
| AGENTS.md | 在该范围持续适用的短规则和细节链接 |

同一事实的长篇解释只维护一个主要位置。其他位置保留必要摘要并使用可检查的相对链接。调用者必须知道的条件、异常或完成时机可以就地简述：链接不能让当前入口失去可用性。先读更深层的拥有者再调整上层概述，不先把放错位置的内容润色得更长。

## 教程和参考采用不同结构

教程按读者的已有知识安排前置概念和步骤。先完成一个真实任务，再引入更深的可选内容。参考文档按查询对象组织，内容可以详尽。短文用清晰小节区分两种用途，避免为分类而拆出许多新文件。

入口说明面向用户能做什么、看到什么；内部实现细节放到相应深度。目录和摘要在长文中帮助定位，短说明不必套全套栏目。

## 篇幅预算

只约束实际容易膨胀的常驻文件。`.doc-maintenance.json` 的 `budgets` 记录具体路径、计量单位和上限。超过上限时：

1. 将不属于该层级的细节移到其主要归属，修复入链。
2. 删除重复和无关叙述，保护所有必要事实。
3. 内容确有必要且无法合理迁移时，说明理由并调整预算。

可借鉴 DSH 保留约 5% 工作余量的做法，但预算与余量应按项目决定；工具不自动收紧或扩大。英文 `words` 按空白分词；`characters` 数非空白 Unicode 码点，适合明确约束中文/混合文本。两者都计入代码与表格，不是阅读难度评分，也不是模型 token 预算。不要用同一数字直接比较两种单位。

## 当前状态和历史

现行说明写现在的行为，决策说明保存理由与取舍，历史档案保留当时证据。使用项目既有提案、ADR 或设计记录体系即可。

- 仍指导当前实现的说明同步更新事实位置和名称。
- 过时方案指向替代方案；保留仍能防止重犯的否决理由。
- 归档的历史不再作为当前规范，不为了统一文风改写它。
- 机械小改动优先更新已有说明；需要长期保留、且源码和测试无法表达的理由才值得新增决策记录。

篇幅治理不等于按年龄或配额删除历史。移动、删除或合并说明前先查看入链；保留独特理由及已知验证缺口。
