# 保留事实和作者表达

## 改写前后的核对

识别并保留影响使用的事实：谁做什么、什么条件下做、先后顺序、必须/可以/禁止、例外、责任、失败方式和后果。不能仅因新句子更短就接受它。

例如，原句是“关闭时先发出取消请求，再等待后台任务退出；等待失败会返回错误。”只写“关闭会取消任务”丢失了等待和错误保证。可以删重复修饰，不能删这些区别。

“检查输入形态并维护一致性”通常没有“检查请求是否包含 projectId；缺失时返回错误”具体。技术术语如果准确命名实际对象，可以保留；不维护一份无条件禁词表。

## 清理会话视角与思维链泄漏

对可疑段落和注释做一次 **HEAD 自洽检验**：只看着当前仓库 `HEAD`、没有任何聊天记录、PR 讨论或未提交草稿的读者，能否解析每个引用并验证每条陈述？如果不能，先把仍成立的事实改写为立足当前仓库的陈述，再删掉其余会话残留。

重点清理这些高频泄漏：

- **死会话引用**：只存在于草稿或聊天中的编号与代号（如 `(decision 7)`、`audit C2`、`plan §4.7`、`T4`）。有已入库归属就改成明确路径链接，否则删除编号并补全独立事实。
- **PR/分支视角与时间邮戳**：“本 PR 新增”、“后续 PR 处理”、“此前是 X，现在不再 Y”、“这次切分”。直接陈述当前行为或扩展点；延后事项转为明确的 `TODO` 或 issue 引用。
- **评审过程与自辩注释**：“评审中否决了…”、“这里类型转换是安全的因为…”。不要对着已经结束评审的人辩护；直接陈述保证安全的不变式，或删掉代码已经说明白的废话。
- **推导流水账、糊弄词与语言混入**：逐步复述控制流或测试步骤（“先做 X，再做 Y”）、无依据的妥协（“暂时应该够用”），以及单语正文中误混入的另一种工作语言词句。

注意不要误删有效信息：可解析的 issue/PR 编号（如 `#1470`）、用现在时写成的防回归说明（“不做 X 会导致 Y”）、带实测依据的边界标注（如 `(measured: ...)`），以及 lint/覆盖率豁免理由（理由不对时修正，不直接删）。

维护中的文档指向当前文件用相对链接，指向历史用 tag 或 PR/issue 号，避免硬写容易因变基失效的裸 commit SHA。Markdown 正文默认一段一行、靠编辑器软折行，减少改词引起的整段 diff 重排（项目已有折行规范时从其约定）。

## 样例和术语是项目自己的

从项目已经认可的文字里选择少量适用样例，不把 DSH 文风强加给其他作者。记录样例为何好：显式执行者、可验证条件、必要的失败信息、没有实现流水账等。把一次纠正提炼为判断后，检查本次范围内的同类段落。

术语约定至少回答：该概念叫什么、首次出现是否解释、哪些近似叫法会混淆。复用已有术语表；没有稳定项目偏好时先保持当前一致表达。术语或事实与风格样例冲突时优先事实和术语；过时样例中的技术事实不能带入新文档。

## 最小改动

先定位要改的事实、句子和关联说明，保留无关段落。审查时区分应保留、补充、精简、恢复、移动的内容，不只寻找可删文字。解释重复可以合并，关键行为在使用位置仍需清晰。

双语目标是同等信息与自然表达。允许按目标语言重排句法；标题、技术标识符等结构约束由工具配合验证。默认不要求两侧物理行数相同。

## 评审例子

| 发现 | 应采取的行动 | 不足以证明修好的证据 |
|---|---|---|
| 使用了两个名称指同一配置 | 对照源码和术语表统一，并检查关联说明 | 全文替换后没有语法错误 |
| 文档很长 | 判断职责、重复和读者路径后再删改 | 字数下降 |
| 原说明有取消/失败条件 | 改写后逐项核对条件与后果 | 句子更流畅 |
| 一段像开发过程记录 | 保留当前约定；有长期价值的理由归到决策说明 | 简单换掉“之前/现在” |
| 注释带 `(decision 3)` 或“本 PR 确保安全” | 按 HEAD 自洽改写为不变式或当前约束，删会话残留 | 只删编号却丢了安全前提 |
| 教程不易操作 | 实走代表性路径并补必要步骤 | 目录和排版整齐 |
